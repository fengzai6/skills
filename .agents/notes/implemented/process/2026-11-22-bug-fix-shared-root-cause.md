# Agent Note: 修复 Bug 时检查并报告同源风险

Status: implemented

## Problem

局部补丁能消除一处故障，但同一规则由多个入口分别维护时，其他入口仍可能产生同类故障。直到交付时才说清剩余风险，用户已经错过根据影响范围选择本次修法的时机。以直接导致功能错误作为报告门槛，也容易漏掉与当前任务相关的契约、数据和可靠性风险。

## Decision

`dev-standards` 按证据和影响决定报告范围。与当前任务直接相关、可能影响正确性、契约、数据或可靠性的风险应主动报告，说明依据、触发条件和影响。纯风格和可维护性偏好按用户要求提出。扩大改动范围前先取得确认。

修 Bug 时按故障风险检查与根因直接相关的路径，区分已确认受影响的路径、修复后仍有风险的路径和待验证路径。影响本次修法的风险在动手前提出。范围内的低风险问题直接修根因。获准止血时说明覆盖范围和剩余风险。涉及公共契约、数据迁移或范围扩大的根治方案先取得确认。

## Alternatives considered

- 将同源风险统一留到交付汇报，可以维持现有收口节奏。如果风险会影响修法，报告时点会晚于该决策。
- 发现同源风险就暂停全部修复，可以确保用户参与决策，也会延迟已获授权的止血和范围内可直接完成的低风险修复。

## Verification

- 文案改动的模拟场景中，代理报告了已确认的批量导出覆盖风险，并将修复留待授权。
- 发版前的模拟场景里，修订版在动手前说明手工录入补丁仍会留下批量导入缺口，指出离线客户端契约待核实，并给出本次止血的推荐与确认点。
- 单点低风险问题的模拟场景直接修根因。明确授权紧急止血的场景执行局部修复并说明剩余风险，将会改变旧接口契约的根治方案留待确认。

## Consequences

- 用户在选择修法时能看到补丁覆盖范围、复发路径和是否需要扩大修复范围。
- 调试会多一次与根因相关的范围核查。检查深度由故障风险决定，跨范围的修复按实施边界确认。
