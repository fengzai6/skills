# Agent Note: 通用规范的查证确认与文件拆分边界

Status: implemented

## Problem

第一轮去重后的 `rules/main.md` 仍要求任何不确定的技术细节先问用户，并默认把不同关注点分文件。这会把可自行查证的事实交回用户，也可能使简单功能被机械拆分；仅压缩重复文字不能消除这两类执行负担。

仅明确何时拆分还不足以指导文件落位：同一功能或职责的一组相关文件可能持续平铺在同层，只靠文件名前缀区分，需要明确目录归类边界。

## Decision

- 技术事实先通过项目代码、配置和权威资料查证，不编造 API、类型或业务规则。查证后仍缺少必要信息，或存在影响需求、接口契约、数据正确性及实施风险的歧义时，先向用户确认。
- 闭环 Intent 引用同一查证与确认边界，不再单独要求一切不确定都先问。
- 文件按职责和实际复杂度组织；仅在关注点具有独立改动需求，或混放已明显增加理解、验证成本时拆分，不为简单逻辑机械增加文件或抽象。入口仍只做组装编排，不承载复杂业务逻辑。
- 同一功能、领域或职责的一组相关文件，优先按项目现有结构归入对应子目录，避免仅靠重复文件名前缀在同层持续平铺；优先复用已有目录，不为单个文件机械建目录或无实际需要地增加嵌套。本次只补规范，不调整现有文件路径。
- §2.2 的超过 500 行评估和拆分前确认保持不变；测试、笔记、Git 授权、任务分流和 skill 触发范围不变。

本决策补充 [第一轮保守去重](../../implemented/process/2026-11-03-main-rules-deduplication.md) 的确认与模块化边界，不取代其分流和调用流程去重决定；两篇互链。TypeScript 分册与报价记录不受本决策影响。

## Alternatives considered

- **仅维持第一轮文字去重（未采用）**：能够保留全部执行习惯，但不能减少上述可查证事实的提问和简单逻辑的机械拆分。
- **调整查证确认、按复杂度拆分并明确目录归类（采用）**：区分查证与确认、拆分与归类，既减少机械拆分，也约束相关文件持续平铺；不改变拆分授权、测试或 skill 加载策略，代价是需要判断信息是否充分、文件职责和归类是否合理。

## Verification

- 以第二轮开始时已暂存的第一轮正文为基线，核对差异仅涉及核心原则的查证确认、闭环 Intent 和 §2.4 模块化规范；其余正文不变。
- 逐项检查事实可查证、必要信息缺失、关键歧义、简单逻辑、复杂入口、相关文件归类及避免机械嵌套等场景；§2.2 原文及其拆分授权保留。
- 使用 `node scripts/count-tokens.mjs` 更新 README 并复核数字；运行 `git diff --check`，核对本轮没有改变暂存区。
- 从仓库根目录使用 Node.js 24 运行已加载笔记 skill 的目录、格式和归档三个校验脚本，不增加项目依赖。

## Consequences

- 规范区分可查证事实与需要用户决定的歧义，并允许简单逻辑保留在同一文件；减少提问不等于允许猜测业务或自行改变已确认方案。
- 需要判断信息是否充分、混放是否已造成理解或验证成本；超过 500 行仍须评估，执行拆分仍须确认。
- 一组相关文件以目录表达归属，代价是增加必要的目录层级；沿用现有分类并避免单文件机械套目录，防止用过度嵌套替代平铺。
- 文字校验不能证明实际执行一定减少提问或拆分；后续若仍出现事实性提问或机械拆分，应依据具体任务复核触发条件，不以进一步放宽范围或授权作为默认解法。
