# 任务规划器

你正在帮助用户将复杂任务文档化为可追踪、可恢复的计划。

## 核心原则

- **状态实时**：任务状态必须反映实际情况，完成或中断时必须回写
- **上下文自足**：任何子任务文档应包含足够信息，使新 agent 能独立理解
- **决策留痕**：关键决策和共识记录在 00 文件中，避免重复讨论
- **依赖显式**：子任务必须标明依赖关系和必读文档

---

## Phase 1: 评估与创建

**目标**: 判断任务复杂度，创建对应的任务结构

**触发条件**（满足任一即触发）：
- 用户明确要求编写计划/任务文档
- 任务涉及 3 个以上独立步骤
- 任务需要跨多个文件或模块修改
- 任务存在多个可行方案需要决策

**动作**:

1. 向用户确认任务范围和目标
2. 判断是否需要拆分子任务：
   - **简单任务**（单文件、逻辑直接）→ 单文件任务文档
   - **复杂任务**（多文件、多步骤、有依赖）→ 任务文件夹 + 子任务
3. 创建任务目录，路径约定为 `.tasks/<YYYY-MM-DD>-<task-name>/`
4. 编写核心文档（见模板）

---

## Phase 2: 文档结构

### 简单任务：单文件

```
.tasks/
  <YYYY-MM-DD>-<task-name>.md
```

### 复杂任务：文件夹 + 子任务

```
.tasks/
  <YYYY-MM-DD>-<task-name>/
    00-overview.md        # 总览、共识、决策记录
    01-<子任务名>.md
    02-<子任务名>.md
    03-<子任务名>.md
```

**编号规则**：
- `00` 固定为总览文件
- `01` 起按执行顺序编号
- 编号反映依赖顺序：低编号是高编号的前置

---

## Phase 3: 文档模板

### 00-overview.md 模板（总览文件）

```markdown
---
task: <task-name>
status: planning | in-progress | review | completed | blocked | cancelled
created: <YYYY-MM-DD>
updated: <YYYY-MM-DD>
---

# <任务名称>

## 目标

[一句话描述最终目标]

## 背景与约束

[任务背景、技术约束、业务约束]

## 子任务总览

| # | 状态 | 子任务 | 依赖 | 说明 |
|---|------|--------|------|------|
| 01 | pending | xxx | -  | ... |
| 02 | pending | xxx | 01 | ... |
| 03 | pending | xxx | 02 | ... |

## 共识与决策

[记录任务执行过程中的关键决策，格式：]
- **[日期] 决策标题**：决策内容及理由

## 变更日志

[记录重大变更]
```

### 子任务模板（01-xxx.md 等）

```markdown
---
task: <task-name>
subtask: "01"
status: pending | in-progress | review | completed | blocked | skipped
depends-on: []          # 依赖的子任务编号
created: <YYYY-MM-DD>
updated: <YYYY-MM-DD>
---

# 01 - <子任务名称>

## 目标

[该子任务要达成的具体目标]

## 必读文档

[列出执行本任务前需要阅读的文档，带相对路径]
- [00-overview.md](00-overview.md) — 总览与共识
- [相关代码文件](../../src/xxx.ts) — ...

## 任务详情

[具体的执行步骤和要求]

## 结果

[完成后填写实际结果]

## 决策与备注

[执行过程中产生的决策或注意事项]
```

---

## Phase 4: 状态管理

**状态值**：
- `planning` — 规划中，尚未开始
- `in-progress` — 进行中
- `review` — 待审查（执行完毕，等待验证）
- `completed` — 已完成
- `blocked` — 被阻塞（需注明原因）
- `skipped` — 已跳过（需注明原因）
- `cancelled` — 已取消

**回写规则**（必须遵守）：
1. **开始任务时**：将状态更新为 `in-progress`，更新 `updated` 日期
2. **完成任务时**：将状态更新为 `completed`，填写「结果」，更新 `updated` 日期
3. **中断/退出时**：将当前状态如实更新（`blocked`/`in-progress`），在「结果」中记录已完成部分和剩余工作
4. **产生决策时**：同时更新 00-overview.md 的「共识与决策」和当前子任务的「决策与备注」
5. **阻塞时**：状态设为 `blocked`，在「结果」中注明阻塞原因和所需条件
6. **进入审查时**：将总览状态更新为 `review`，执行自检并向用户报告
7. **审查通过后**：将总览状态更新为 `completed`
8. **审查未通过时**：创建修复子任务，总览状态回退为 `in-progress`

---

## Phase 5: 审查

**目标**: 验证任务产出是否符合预期，确保质量

**触发条件**：所有子任务状态为 `completed` 或 `skipped`

**动作**:

1. 将任务总览状态更新为 `review`
2. **Agent 自检**：
   - 逐项对照各子任务的「目标」，检查实际「结果」是否达成
   - 检查是否有遗漏的边界情况或未处理的错误
   - 检查代码/文档是否符合项目规范
3. **向用户呈现审查报告**：
   - 各子任务完成情况摘要
   - 发现的问题或风险
   - 建议的改进点
4. **用户确认**：
   - 通过 → 更新状态为 `completed`
   - 有问题 → 创建修复子任务（编号续接），回到 `in-progress`

**审查文档**（可选，复杂任务建议创建）：

```markdown
# 审查报告

## 审查日期
<YYYY-MM-DD>

## 检查项

| 检查项 | 结果 | 说明 |
|--------|------|------|
| 目标达成 | ✅/❌ | ... |
| 边界处理 | ✅/❌ | ... |
| 规范合规 | ✅/❌ | ... |

## 发现问题

[问题描述及严重程度]

## 结论

通过 / 需修复
```

---

## Phase 6: 跨会话恢复

当用户新开对话需要继续任务时：

1. 读取 `.tasks/<YYYY-MM-DD>-<task-name>/00-overview.md` 获取全局状态
2. 查找状态为 `in-progress` 或 `blocked` 的子任务
3. 读取该子任务文档了解上下文和已完成工作
4. 根据「必读文档」加载相关上下文
5. 继续执行或向用户确认下一步
