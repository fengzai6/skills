# 任务规划器

你正在帮助用户判断任务是否需要文档化规划，并在确有必要时创建可追踪、可恢复的计划。

## 核心原则

- **按需文档化**：只有任务确实需要跨会话恢复、多人/多 agent 交接、复杂依赖或用户明确要求时，才创建 `.tasks` 文档
- **低摩擦优先**：需求清晰、风险可控、预计当前会话可完成的任务，不落文档；只在对话中简短拆分并执行
- **状态真实**：已创建任务文档时，状态必须反映实际情况；在开始、完成、阻塞、中断等关键节点回写
- **上下文自足**：任何子任务文档应包含足够信息，使新 agent 能独立理解
- **决策留痕**：关键决策和共识记录在 00 文件中，避免重复讨论
- **依赖显式**：子任务必须标明依赖关系和必读文档
- **计划需确认**：任务处于 `planning` 状态时，用户的所有反馈都视为计划修改要求；只有用户明确确认 OK 后，才能将状态改为 `pending` 或直接开始执行

## 文档写入规则

### 纠正与补充

当用户纠正方向或补充要求时：
- 只把**修正后的最终结论**写入文档
- **不记录**纠正发生的过程
- 如果原文档中已有错误上下文，**直接替换**为正确上下文，而不是追加解释

### 共识与决策的记录标准

「共识与决策」**只记录**会影响后续执行的稳定决策：
- ✅ 技术选型、边界约束、依赖关系、实施顺序、取舍理由

**不要记录**：
- ❌ 对 agent 行为的要求
- ❌ 沟通纠偏过程
- ❌ 提示词相关问题

### 写入前自检

不确定某条信息是否应该写入时，先判断：
1. 未来读者不知道这条信息会不会做错？
2. 这条信息是否会影响后续实现或判断？
3. 这条信息是否是最终结论，而不是讨论过程？

只有以上至少一个答案为「是」，才可以写入；否则不要写入。

## Phase 1: 评估与分层

**目标**: 判断任务是否需要文档化规划，并选择最轻的可行流程

**应使用文档化计划的条件**（满足任一即触发）：
- 用户明确要求编写计划/任务文档
- 任务需要跨会话恢复或交接给新 agent
- 任务存在多个可行方案，且需要先决策再执行
- 任务影响面较大、风险较高，或涉及多个模块之间的依赖顺序
- 任务预计无法在当前会话内可靠完成

**不应仅因以下情况触发文档化计划**：
- 只是跨多个文件
- 只是超过 3 个操作步骤
- 需求清晰、风险可控、可以当前会话完成

**动作**:

1. 判断任务分层：
   - **轻量任务**：需求清晰、风险可控、当前会话可完成 → 不创建 `.tasks`，只在对话中简短拆分步骤并执行
   - **中等任务**：步骤较多但不需要跨会话恢复 → 使用对话内 checklist 或可用的计划工具追踪，不落文档
   - **重型任务**：满足文档化计划触发条件 → 创建任务文件夹 + 子任务文档
2. 若任务目标、范围或关键约束不清晰，先向用户确认；已清晰时直接进入对应流程
3. 只有重型任务需要落文档：
   - 先用简要文字说明任务拆分思路和子任务规划
   - 用户确认方向后，创建任务目录，路径约定为 `.tasks/<YYYY-MM-DD>-<task-name>/`
   - 编写核心文档初稿（见模板），状态设为 `planning`
   - 根据用户反馈迭代更新，直到用户确认 OK
   - 用户确认后，根据指示将状态改为 `pending` 或直接开始执行

## Phase 2: 文档结构

### 轻量任务：不落文档

适用于需求清晰、风险可控、当前会话可完成的任务。只在对话中保留简短步骤和执行结果。

### 中等任务：对话内追踪

适用于步骤较多但不需要跨会话恢复的任务。使用 checklist 或可用的计划工具追踪状态；除非用户明确要求，否则不创建 `.tasks` 文件。

### 重型任务：文件夹 + 子任务

```
.tasks/
  <YYYY-MM-DD>-<task-name>/
    00-overview.md        # 总览、共识、决策记录
    01-<子任务名>.md
    02-<子任务名>.md
    03-<子任务名>.md
```

**编号规则**：
- `00` 固定为总览文件
- `01` 起按执行顺序编号
- 编号反映依赖顺序：低编号是高编号的前置

## Phase 3: 文档模板

### 00-overview.md 模板（总览文件）

```markdown
---
task: <task-name>
status: planning | in-progress | review | completed | blocked | cancelled
created: <YYYY-MM-DD>
updated: <YYYY-MM-DD>
---

# <任务名称>

## 目标

[一句话描述最终目标]

## 背景与约束

[任务背景、技术约束、业务约束]

## 子任务总览

| # | 状态 | 子任务 | 依赖 | 说明 |
|---|------|--------|------|------|
| 01 | pending | xxx | -  | ... |
| 02 | pending | xxx | 01 | ... |
| 03 | pending | xxx | 02 | ... |

## 共识与决策

[只记录会影响后续执行的稳定决策，格式：]
- **[日期] 决策标题**：决策内容及理由

[适用范围：技术选型、边界约束、依赖关系、实施顺序、取舍理由]
[不要记录：agent 行为要求、沟通纠偏、提示词问题、讨论过程]

## 变更日志

[记录重大变更]
```

### 子任务模板（01-xxx.md 等）

```markdown
---
task: <task-name>
subtask: "01"
status: pending | in-progress | review | completed | blocked | skipped
depends-on: []          # 依赖的子任务编号
created: <YYYY-MM-DD>
updated: <YYYY-MM-DD>
---

# 01 - <子任务名称>

## 目标

[该子任务要达成的具体目标]

## 必读文档

[列出执行本任务前需要阅读的文档，带相对路径]
- [00-overview.md](00-overview.md) — 总览与共识
- [相关代码文件](../../src/xxx.ts) — ...

## 任务详情

[具体的执行步骤和要求]

## 结果

[完成后填写实际结果]

## 决策与备注

[执行过程中产生的决策或注意事项]
```

## Phase 4: 状态管理

**状态值**：
- `planning` — 规划中，尚未开始
- `in-progress` — 进行中
- `review` — 待审查（执行完毕，等待验证）
- `completed` — 已完成
- `blocked` — 被阻塞（需注明原因）
- `skipped` — 已跳过（需注明原因）
- `cancelled` — 已取消

**回写规则**（仅适用于已创建 `.tasks` 文档的任务）：
1. **开始执行重型任务时**：将总览或当前子任务状态更新为 `in-progress`，更新 `updated` 日期
2. **完成子任务时**：将子任务状态更新为 `completed`，填写「结果」，更新 `updated` 日期，并同步 00-overview.md 的子任务总览
3. **中断/退出时**：将当前状态如实更新（`blocked`/`in-progress`），在「结果」中记录已完成部分和剩余工作
4. **产生关键决策时**：同时更新 00-overview.md 的「共识与决策」和当前子任务的「决策与备注」
5. **阻塞时**：状态设为 `blocked`，在「结果」中注明阻塞原因和所需条件
6. **进入审查时**：将总览状态更新为 `review`，执行自检并向用户报告
7. **审查通过后**：将总览状态更新为 `completed`
8. **审查未通过时**：创建修复子任务，总览状态回退为 `in-progress`

---

## Phase 5: 审查

**目标**: 验证任务产出是否符合预期，确保质量

**触发条件**：已创建 `.tasks` 文档，且所有子任务状态为 `completed` 或 `skipped`

**动作**:

1. 将任务总览状态更新为 `review`
2. **Agent 自检**：
   - 逐项对照各子任务的「目标」，检查实际「结果」是否达成
   - 检查是否有遗漏的边界情况或未处理的错误
   - 检查代码/文档是否符合项目规范
3. **向用户呈现审查报告**：
   - 各子任务完成情况摘要
   - 发现的问题或风险
   - 建议的改进点
4. **审查结论**：
   - 自检和必要验证通过 → 更新状态为 `completed`
   - 用户要求复查或发现问题 → 创建修复子任务（编号续接），回到 `in-progress`

**审查文档**（可选，重型任务建议创建）：

```markdown
# 审查报告

## 审查日期
<YYYY-MM-DD>

## 检查项

| 检查项 | 结果 | 说明 |
|--------|------|------|
| 目标达成 | ✅/❌ | ... |
| 边界处理 | ✅/❌ | ... |
| 规范合规 | ✅/❌ | ... |

## 发现问题

[问题描述及严重程度]

## 结论

通过 / 需修复
```

---

## Phase 6: 跨会话恢复

当用户新开对话需要继续任务时：

1. 读取 `.tasks/<YYYY-MM-DD>-<task-name>/00-overview.md` 获取全局状态
2. 查找状态为 `in-progress` 或 `blocked` 的子任务
3. 读取该子任务文档了解上下文和已完成工作
4. 根据「必读文档」加载相关上下文
5. 继续执行或向用户确认下一步

## 完成检查清单

- [ ] 已选择最轻的可行流程（轻量 / 中等 / 重型）
- [ ] 若创建了 `.tasks` 文档，用户已确认计划（planning → pending/in-progress）
- [ ] 若创建了 `.tasks` 文档，所有子任务状态已更新
- [ ] 若创建了 `.tasks` 文档，00-overview.md 中子任务总览表状态与实际一致
- [ ] 关键决策已记录在合适位置（重型任务写入 00-overview.md；轻量/中等任务在对话中说明）
- [ ] 若创建了 `.tasks` 文档，每个子任务的「结果」已填写
- [ ] Agent 自检通过（目标达成、边界处理、规范合规）
- [ ] 若创建了 `.tasks` 文档，变更日志已更新
