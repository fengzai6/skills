# Spec 文档审查

## 快速开始

用户提供 spec 文档路径或内容，按下方审查维度逐项分析，输出结构化审查报告。

## 工作流

1. **读取文档** — 完整阅读用户提供的 spec 文档，理解全部内容
2. **逐维度审查** — 按下方 6 个维度依次分析
3. **输出报告** — 按严重程度分级输出，末尾给出整体评价

## 审查维度

### 1. 完整性

- 是否遗漏核心需求或功能点
- 是否覆盖异常路径和边界条件
- 是否考虑非功能需求（性能、安全、可扩展性等）
- 是否明确外部依赖和前置条件

### 2. 清晰性

- 描述是否无歧义，关键术语是否一致
- 核心决策是否有依据（为什么选 A 不选 B）
- 数据结构、接口定义是否明确
- 是否存在逻辑矛盾或自相矛盾的描述

### 3. 设计合理性

- 方案是否过度设计或设计不足
- 是否与项目现有架构和模式一致
- 关注点分离是否合理
- 是否有不必要的耦合

### 4. 替代方案

- 是否有更简洁的实现路径
- 是否有更成熟的方案或设计模式可借鉴
- 给出对比和推荐理由

### 5. 可行性与风险

- 技术依赖是否明确、是否可用
- 假设条件是否成立
- 潜在风险点和降级方案
- 是否有性能隐患或安全隐患

### 6. 范围边界

- 是否有越界内容（超出需求的额外发挥）
- 是否有遗漏的边界 case
- 实现范围是否可控

## 输出格式

按严重程度分级：

- **阻塞** — 必须修改，否则无法推进
- **建议修改** — 影响质量或可维护性，强烈建议改
- **可选优化** — 锦上添花，不影响核心功能

每个问题附带：
1. 问题描述
2. 建议方案
3. 修改示例（如适用）

末尾总结：
- 整体评价（一句话）
- 最值得改进的 1-2 个点
