# 通用开发规范

## 适用范围与入口

- 按当前任务内容判断，在相关分析或操作前读取本规范；是否打开代码仓库、是否已有本地文件不作为触发依据。
- 纯概念解释、普通写作或日常问答按全局规则及实际匹配的其他 skill 处理；同一对话转入开发任务时再加载本规范。

## 1. 实施边界

- **遵循项目现有风格与简洁实现**：匹配项目现有的代码风格和约定，不自作主张改变；能简短实现就保持简短，不为外观添加抽象；排版疏密适中，避免挤成一团或无意义空行。
- **发现关键缺口先确认**：他方必要信息未到位、方案存在影响需求或契约的歧义、做法会导致功能错误或高返工成本时，先停笔，指出问题并给建议方案，等确认再写；例如后端未提供 `hasMore` / `total`，不能用 `list.length > 10` 猜测。
- **建议范围**：不额外提出代码风格、命名偏好、性能微优化或可维护性建议，除非直接导致功能错误或用户要求。
- **未提交实现的调整边界**：当前任务涉及的本地未提交实现可大幅调整或重写，不必为其保留兼容层、迁移逻辑或过渡方案；仍须遵守已确认需求，不覆盖无关用户改动。
- 未提交不等于未运行；涉及数据库、文件或外部系统的实际影响，仍须核实并处理。Git 写操作继续遵循全局授权规则。

## 2. Loop Engineering（闭环工程）

Loop Engineering 是开发任务的默认编排方式：尽可能把任务拆成可观察、可验证、可退出的小闭环，依次完成并检查。

### 2.1 完整闭环

每个完整 loop 按以下顺序推进：

1. **Intent（意图）**：确认目标、边界、非目标、完成标准和退出条件（如用户确认、测试通过、问题复现消失）；缺失先补齐，按全局规则的「查证与确认」处理不确定事项，不猜测。
2. **Plan（路径）**：按 §2.2 任务分流选择最轻可行载体。
3. **Act（执行）**：只做当前 loop 的最小必要改动；不扩大范围，不顺手重构无关内容。
4. **Check（检查）**：用 diff、测试、脚本输出、截图或人工确认等证据检查结果；声称完成前必须经过检查。
5. **Adjust（修正）**：检查失败不能结束，修正后回到 Check；检查通过才进入下一个 loop。
6. **Close（收口）**：说明完成内容、验证证据和剩余风险；不要把过程噪音写入文档。

### 2.2 任务分流与升级

| 任务 | 判断条件 | 执行方式 |
| --- | --- | --- |
| 轻量 | 需求清晰、低风险，如修小 bug、补函数、当前会话可完成 | 直接做；会话内 TODO / checklist 可选，不调用 grilling / Superpowers，不写 spec / plans |
| 中等 | 需求模糊，但任务不大 | `/grilling` 对齐后用短方案或会话内 TODO 跟踪；不升级 Superpowers，不默认落文档，不落设计文档 |
| 重型 | 任务大、风险高、需要审计和对齐，如跨模块、多方案、跨会话或用户要求计划文档 | Superpowers（`brainstorming`），升级为 spec / plans / subagent 编排，确认后再实施；需求已清晰时不必再 grilling |

只有当前 loop 的信息不足、风险过高或无法可靠恢复时才升级，不为流程完整而升级。

## 3. 通用代码规范

### 3.1 命名规范

- **命名约定**：文件、目录和代码符号遵循目标项目的明确规范；没有明确规定时，采用所属语言或框架的惯例及对应专项 skill，不全局统一大小写风格。
- **混合技术栈**：按文件或模块所属技术栈分别执行，不将一种语言的命名风格套用到其他语言。
- **通用化产物命名**：名称贴近产物本身的功能或用途，而非使用场景。

### 3.2 文件与复用规范

- **优先复用现有实现**:
  - 对于已有的逻辑、能力或结构，优先复用现有实现，不要重复造轮子。
  - 开始新增实现前，按目标项目实际结构查找已有可复用的函数、模块、组件、hook、类型或配置，不限定目录名称；确认没有合适实现后再新增。
- **优先使用外部依赖**:
  - 项目已引入的组件库、工具库、协议库等，必须优先使用，不得自行实现等价功能。
  - 例如：能用组件库的组件就不要手写 HTML/CSS；能用已封装的网络请求库就不要自己写协议解析；能用已有的日期/校验/表单等工具库就不要自己造轮子。
  - 只有当已有依赖确实无法满足需求（功能缺失、性能瓶颈、兼容性问题）时，才可以自行实现，但需简要说明理由。
- **重复逻辑应抽离复用**:
  - 对于重复出现或明显可复用的代码，应优先考虑抽离为公共实现。
  - 抽离时应结合项目现有结构，优先放入合适的公共目录，而不是随意新增层级。
- **文件拆分**:
  - 单个文件代码超过 500 行就需要考虑是否可以进行拆分优化；
  - 如果可以拆分，需询问同意后进行。

### 3.3 模块化与注释

- 按职责和实际复杂度组织文件；入口只做组装编排，不承载复杂业务逻辑。
- 仅在关注点具有独立改动需求，或混放已明显增加理解、验证成本时拆分，不为简单逻辑机械增加文件或抽象；超过 500 行的评估与拆分前确认仍按 §3.2 执行。
- 同一功能、领域或职责的一组相关文件，优先按项目现有结构归入对应子目录，避免仅靠重复文件名前缀在同层持续平铺；优先复用已有目录，不为单个文件机械建目录或无实际需要地增加嵌套。
- 注释只写理解当前行为所需的 non-obvious reason，不记录历史方案或 intermediate attempts。

### 3.4 测试规范

- **依赖前提**：项目有 Jest、Vitest、pytest 等测试相关依赖才可编写测试；没有则不写。
- **按行为复杂度选择**：优先聚焦分支、循环、状态、错误处理或业务不变量；有分支、循环、状态机、协议/金额/权限/安全路径，或用户明确要求，才写。不以「是不是函数 / 纯函数 / 工具方法」判断是否补测。
- **简单逻辑不写**：直给映射、透传、委托、单行转换、无分支无循环无状态、纯展示/布局、配置声明、类型定义、re-export，以及测试只能复述实现（改实现必改测试、几乎没有失败可能）的情况。
- **直接引用实现**：禁止在测试中重写业务逻辑；断言必须基于已确认的行为，不确定先问，不能猜测。
- **UI 测试**：非必要不主动编写，除非用户要求。

## 4. 重要改动必须留笔记

- **适用范围**：涉及行为、架构、跨文件契约、流程与工具链、测试策略、落盘 / 网络 / 配置格式的非平凡改动，实施前调用 `/write-notes-like-deepseek`，写或更新决策笔记。笔记用于保留决策依据，不替代 spec / plans，也不因写笔记自动升级任务流程。
- **机械性改动免写**：纯样式、格式化、打标、不改行为的补丁等机械性改动无需笔记；免写不代表可以自动提交，git 操作仍须用户明确要求。
- **先检索，再落笔**：优先沿用项目已有的决策记录目录；没有约定时使用 `.agents/notes/`。写前检索同主题旧笔记，已有归属就地更新，不重复建篇。未落地方案放入 `proposed/`，落地时随实现变更同步转入 `implemented/`；新决策完全取代旧决策时，同批归档旧篇，并在新笔记中标明替代关系。
- **只记有效决策**：写清最终决策、关键约束、必要的取舍依据和验证结果；不记录讨论过程或中间尝试。未采纳方案仅在其取舍理由有助于理解最终决策时简要记录，并标明未采纳；尚未落地的提案明确标注状态，不写成已实现事实。
- **提交前校验**：涉及笔记的改动，提交前必须按 `/write-notes-like-deepseek` 说明使用适配项目的入口并通过校验。缺少入口或依赖时先确认，不擅自添加工具链；校验失败先修复，不带失败提交。

## 5. 专项 skill

按当前开发任务的实际触发条件读取匹配项，先流程类、再实现类；必须先读取再开展相关分析或操作，不因任务简单、仅做代码问答或用户未点名而跳过。下表不是穷举，其他项目与系统 skill 按实际触发条件判断。

| 触发条件 | Skill |
| --- | --- |
| 涉及 TypeScript / TS / TSX、`tsconfig.json`、类型定义（含 Node.js 后端、脚本、工具链），或 React / Next.js 组件、hooks、路由、状态管理、样式 | `/ts-standards` |
| 用户要求审查测试，或即将开 PR、大任务完成后可能遗漏测试 | `/test-review` |
| 用户要求审查代码变更、diff、commit 或实现 | `/code-review` |
| 用户要求审查 PR、提供 PR 编号/URL，或对分支变更集做 review | `/pr-review` |
| 用户要求处理 PR review comment，或提供 review 结论要求跟进 | `/handle-review` |

涉及调试、测试、实现功能或代码变更时，还须检查对应系统 skill（如 `systematic-debugging`、`test-driven-development`）；`grilling` / Superpowers 仅按开发任务分流触发，不因有代码变更自动调用 `brainstorming`。Git 操作按全局规则调用 `/git-workflow`。

## 6. 应用示例

- 在代码仓库里让助手润色邮件：按普通写作处理，不加载本规范。
- 在空目录里要求编写脚本：先加载本规范，再按语言和任务加载对应 skill。
- 只问“什么是数据库事务”：解释概念；若转为设计项目的事务边界，再加载本规范。
