# 业务路线图

从业务全局梳理发展方向、关键阶段和成功判据，不进入实现细节。

## 工作流

1. 先确认规划对象、现状、目标、边界和已有约束；信息不足时逐项询问，不猜测。
2. 对话中先提出宏观结构和核心判断，与用户对齐。
3. 用户确认后整理为 Markdown 文档。
4. 用户未指定路径时，查看项目现有文档结构并建议位置；确认后再写入。

## 内容结构

按实际情况裁剪，只保留关键内容：

- 愿景与目标
- 核心业务方向：方向名称、一句话说明、期望形成的业务结果
- 演进阶段：按能力成熟度或业务推进逻辑划分，不绑定时间
- 关键依赖与风险
- 成功判据

## 边界

- 只做业务层宏观方向，不拆项目任务、子任务或执行清单。
- 不写时间计划、周/月/季度/年度安排、里程碑日期或人天。
- 不写技术方案、功能设计、API、数据模型、代码路径或实施步骤。
- 技术只作为业务能力依赖出现，不展开实现方式。
- 不替代 Superpowers 的 spec、plans 或实施计划；需要执行级规划时明确转交。

## 红线

- 用户未主动要求时，不启动宏观规划。
- 规划对象、目标或边界不清晰时，不直接生成文档。
- 用户未确认内容前不落盘；未确认路径时先建议、再写入。
- 不用任务、工期、功能或技术细节填充规划。
